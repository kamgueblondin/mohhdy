# AOS-257 à AOS-264 — transport TCP du handshake X25519 et post-flight AES-GCM

## Périmètre livré

Ce macro-lot relie le flight client TLS fondé sur X25519 au transport TCP déjà présent dans le noyau. Le code compose le flight dans un segment TCP, suit les séquences transport, accepte ensuite le ChangeCipherSpec serveur en clair, vérifie le Finished serveur protégé par AES-128-GCM et permet l’ouverture des premiers records applicatifs chiffrés.

| Composant | Livraison |
|---|---|
| `net_tcp_connection_build_tls_x25519_flight` | Construit ClientKeyExchange, ChangeCipherSpec et Finished dans un payload TCP unique de 93 octets. |
| Atomicité émission | Restaure connexion TCP, handshake, contexte X25519, transcript, session AEAD, master secret, key block et longueur publiée sur erreur. |
| `net_tls_server_finished_verify_data` | Produit les 12 octets `server finished` à partir du transcript et du master secret. |
| `net_tcp_connection_accept_tls_x25519_postflight` | Accepte ChangeCipherSpec, déchiffre Finished avec la session AEAD, le vérifie et l’ajoute au transcript. |
| Records applicatifs | Les helpers TCP/AES-GCM existants sont validés après handshake complet, avec séquences TLS cohérentes. |

## Séquence validée

Le flight local de 93 octets est encapsulé dans un segment TCP de 113 octets, en incluant l’en-tête TCP de 20 octets. L’émission reste soumise au suivi d’ACK et à la limite de retransmission du transport. Après le flight, le client attend un ChangeCipherSpec de six octets, puis un Finished serveur chiffré avec le numéro de séquence AEAD zéro. Sur un tag ou un verify_data invalide, le contexte TCP, le numéro de séquence de lecture AEAD, le transcript et l’automate TLS sont restaurés.

> Le scénario de test falsifie le tag du Finished serveur avant de soumettre le record valide. Le rejet ne consomme ni octet TCP, ni séquence AEAD, ni transition de handshake. Le record valide est ensuite accepté et la session atteint l’état TLS complet.

## Contrat mémoire

Toutes les sorties et tous les workspaces demeurent possédés par l’appelant. L’API ne recourt à aucune allocation dynamique. Le buffer TCP, le buffer des trois records TLS, le transcript, le master secret, le key block, le contexte X25519 et les workspaces X25519/PRF doivent rester valides pendant l’opération.

## Limites explicites

La démonstration valide l’orchestration cryptographique et transport sur des buffers unitaires. La validation complète de soumission obtient **342/342 tests réussis**, un build i386 freestanding réussi et les smoke tests `qemu-ai-provider` et `qemu-ne2k-status` réussis. Le chemin de production ne déclenche pas encore automatiquement cette API depuis la réception réelle des messages handshake fragmentés. La chaîne X.509, les dates, l’hôte, les certificats clients, HTTP, l’encodage HTTP/1.1 et les appels LLM HTTPS de bout en bout restent absents. X25519 reste fonctionnel mais le backend bigint ne fournit pas encore une garantie constante-temps contre les canaux auxiliaires.
