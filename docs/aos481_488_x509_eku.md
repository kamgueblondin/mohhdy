# AOS-481 à AOS-488 — ExtendedKeyUsage X.509 pour les feuilles TLS

**Auteur :** Manus AI  
**Statut :** implémenté et validé localement  
**Périmètre :** parseur DER/X.509 freestanding, politique d’identité TLS, tests Unity

## Objectif

Ce macro-lot ajoute la prise en compte de l’extension X.509 **ExtendedKeyUsage** (EKU) dans le chemin de validation TLS. La pile accepte désormais une feuille dont l’EKU est absente, mais refuse une feuille qui porte l’extension sans déclarer la finalité **TLS Web Server Authentication** (`serverAuth`). Cette finalité est identifiée par l’OID `1.3.6.1.5.5.7.3.1`.

> RFC 5280 définit EKU comme une séquence de finalités de clé et précise qu’une application peut exiger la présence d’une finalité particulière avant d’accepter un certificat [1].

L’implémentation reste **freestanding i386**, sans allocation dynamique. Toutes les données DER restent référencées depuis le buffer fourni par l’appelant ; aucun certificat, OID ou champ d’extension n’est copié dans un stockage caché.

## Modification fonctionnelle

| Élément | Comportement livré |
|---|---|
| OID d’extension EKU | Reconnaissance de `2.5.29.37` (`55 1d 25`). |
| Valeur `extnValue` | Décodage strict d’une `SEQUENCE OF OBJECT IDENTIFIER` encapsulée dans l’`OCTET STRING`. |
| OID `serverAuth` | Détection de `1.3.6.1.5.5.7.3.1` (`2b 06 01 05 05 07 03 01`). |
| Vue de certificat | Ajout des indicateurs `extended_key_usage_present` et `extended_key_usage_server_auth`. |
| Politique TLS directe | Rejet avant validation de chaîne si EKU est présente et ne contient pas `serverAuth`. |
| Politique TLS avec intermédiaire | Même règle appliquée avant la validation `leaf → intermediate → trust anchor`. |

Le parseur impose que l’extension EKU soit unique, que son contenu interne soit une séquence DER complète, non vide et composée uniquement d’OID. Un contenu tronqué, une séquence mal formée ou une seconde EKU fait donc échouer le parsing du certificat.

## Règle de décision TLS

La règle appliquée à une feuille est volontairement explicite :

| Présence d’EKU | `serverAuth` présent | Décision de la politique TLS |
|---|---:|---|
| Non | — | Acceptée par cette règle ; les autres validations restent obligatoires. |
| Oui | Oui | Acceptée par cette règle. |
| Oui | Non | Refusée. |

Cette règle ne remplace pas les contrôles déjà présents : signature et chaîne RSA, liaison AKI/SKI lorsqu’elle est disponible, autorisation CA de l’intermédiaire, `pathLenConstraint`, hostname DNS et fenêtre de validité UTC restent vérifiés dans leurs couches respectives.

## Vecteur DER de non-régression

Un certificat synthétique de **102 octets** ajoute une extension EKU `serverAuth`. Le vecteur encode strictement la hiérarchie suivante :

```text
Certificate ::= SEQUENCE {
  tbsCertificate      SEQUENCE { …,
    extensions [3] EXPLICIT SEQUENCE {
      Extension ::= SEQUENCE {
        extnID    id-ce-extKeyUsage,
        extnValue OCTET STRING {
          SEQUENCE { id-kp-serverAuth }
        }
      }
    }
  },
  signatureAlgorithm  SEQUENCE { OID 1.2 },
  signatureValue      BIT STRING
}
```

Les longueurs DER sont vérifiées par construction : la séquence externe a une valeur de `0x64` (100 octets), le `TBSCertificate` une valeur de `0x59` (89 octets), le wrapper `[3]` une valeur de `0x17` et la séquence `Extensions` une valeur de `0x15`. Ce contrôle évite que le test masque une erreur de framing sous une erreur de politique.

## Limites connues

Cette livraison ne couvre pas encore `anyExtendedKeyUsage`, les finalités autres que `serverAuth`, les politiques d’EKU propagées par une CA, ECDSA/EdDSA, la révocation CRL/OCSP, les chaînes de profondeur arbitraire ni les contraintes de nom. Ces sujets restent des lots distincts. La présente règle est cependant un durcissement directement applicable au chemin HTTPS/TLS existant.
