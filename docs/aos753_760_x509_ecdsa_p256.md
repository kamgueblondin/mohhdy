# AOS-753 à AOS-760 — X.509 ECDSA secp256r1 et validation de chaîne

**Statut : implémenté et validé.** Ce macro-lot étend le parseur X.509 DER caller-owned avec les clés `id-ecPublicKey` sur `secp256r1`/P-256 et permet à la validation de chaîne existante de vérifier une signature de certificat `ecdsa-with-SHA256`. Il s’appuie sur le vérificateur ECDSA P-256/SHA-256 livré par le lot précédent, sans bibliothèque cryptographique externe, sans allocation dynamique et sans copie de certificats.

RFC 5480 définit le champ `SubjectPublicKeyInfo` pour les clés ECC : `id-ecPublicKey` identifie une clé ECC générique, `namedCurve` détermine les paramètres de domaine et la forme non compressée SEC1 est signalée par l’octet `0x04` [1]. FIPS 186-5 décrit la vérification ECDSA comme un mécanisme d’authentification de l’intégrité et de l’origine d’une signature numérique [2].

> **Portée précise.** Une chaîne directe `feuille → ancre` ECDSA/SHA-256 est vérifiée lorsque l’émetteur possède une clé P-256 dans son SPKI. Les chemins RSA/SHA-256 historiques sont conservés à l’identique. Les chaînes ECDSA à intermédiaires, la révocation, les politiques X.509 complètes et le raccordement de `ServerKeyExchange` ECDSA appartiennent aux lots suivants.

## Évolution du modèle de certificat

La structure `x509_certificate_view_t` reste une collection de vues dans le DER détenu par l’appelant. Elle publie maintenant `ec_p256_public_key` et sa longueur, sans allouer ni dupliquer les 65 octets de clé. Les champs RSA demeurent vides pour un SPKI ECC, ce qui empêche tout mélange implicite de mécanismes.

| Élément X.509 | Condition acceptée | Valeur publiée |
|---|---|---|
| Algorithme de clé | `id-ecPublicKey` (`1.2.840.10045.2.1`) | Contenu de l’`AlgorithmIdentifier`. |
| Courbe nommée | `secp256r1` / `prime256v1` (`1.2.840.10045.3.1.7`) | Validée avec l’algorithme de clé. |
| BIT STRING | Aucun bit inutilisé, exactement 65 octets utiles | Vue SEC1 dans `ec_p256_public_key`. |
| Point SEC1 | Premier octet `0x04`, forme non compressée | Accepté au parsing ; l’appartenance à la courbe est contrôlée par ECDSA lors de la vérification. |
| Autre SPKI | Chemin RSA DER historique | Module/exposant RSA publiés comme avant. |

Le parseur refuse une clé ECC dont la taille ou le préfixe SEC1 ne correspond pas au contrat P-256. `x509_ec_p256_public_key_validate` vérifie ensuite de manière explicite l’AlgorithmIdentifier exact, la courbe, la longueur et la forme non compressée. Ce découpage maintient le parsing borné tandis que la validation mathématique du point reste dans la primitive ECDSA unique.

## Validation des signatures de certificat

`x509_certificate_chain_validate_one` calcule toujours `SHA-256(TBSCertificate DER)` dans un contexte local. Le mécanisme est ensuite sélectionné uniquement à partir de l’algorithme de signature du certificat feuille.

| Algorithme de signature feuille | Précondition sur l’émetteur | Vérification |
|---|---|---|
| `sha256WithRSAEncryption` | `rsaEncryption`, module positif et exposant impair pris en charge | `rsa_pkcs1_v15_sha256_verify`. |
| `ecdsa-with-SHA256` | `id-ecPublicKey` + `secp256r1`, SEC1 non compressé de 65 octets | `ecdsa_p256_sha256_verify`. |
| Tout autre algorithme | Aucune | Rejet strict. |

Avant tout calcul cryptographique, le validateur conserve les contrôles déjà présents : présence des vues DER, liaison `issuer → subject` et cohérence AKI/SKI lorsqu’elle est fournie. Pour ECDSA, une signature supérieure à la taille DER maximale P-256 ou un workspace inférieur à `ECDSA_P256_WORKSPACE_WORDS` est rejeté. Le vérificateur P-256 contrôle alors le point de l’émetteur sur la courbe, le DER de la signature et l’égalité ECDSA finale.

## Mémoire et isolation

Aucune voie ne contient `kmalloc`, `malloc`, état cryptographique global mutable ou cache de certificat. Le certificat DER, la clé publique, la signature et le workspace sont tous fournis par l’appelant. La sélection RSA/ECDSA ne copie que le condensat SHA-256 de 32 octets et utilise les espaces de travail existants.

| Ressource | Propriété |
|---|---|
| Certificat et SPKI | Vues `const` dans le DER initial. |
| Clé P-256 | Vue de 65 octets, sans copie. |
| Signature ECDSA | Vue BIT STRING sans octet de bits inutilisés. |
| Hash de TBS | Tableau local fixe de 32 octets. |
| Workspace P-256 | 2 048 mots de 32 bits, fourni par l’appelant. |
| Allocation dynamique | **Aucune.** |

## Tests et résultats de validation

Les tests ajoutent une ancre et une feuille réellement générées localement avec OpenSSL sur `prime256v1`, signées en ECDSA/SHA-256 puis figées en DER. La chaîne a été vérifiée par OpenSSL avant son intégration comme fixture de régression. Le test Unity couvre la publication SPKI, l’algorithme attendu, une validation de chaîne et d’identité positive, ainsi que les rejets ci-dessous.

| Cas vérifié | Résultat attendu |
|---|---|
| SPKI `id-ecPublicKey` / `secp256r1` valide | Vue SEC1 de 65 octets publiée et validée. |
| Feuille ECDSA/SHA-256 réellement signée | Chaîne directe acceptée. |
| Signature de certificat altérée | Rejetée par la vérification ECDSA. |
| Workspace P-256 raccourci d’un mot | Rejeté. |
| Longueur de clé SEC1 modifiée | Rejetée. |
| Algorithme de signature tronqué | Rejeté. |
| Signature DER raccourcie | Rejetée. |
| Régressions RSA existantes | Préservées. |

## Suite logique

Le prochain macro-lot TLS doit annoncer `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`, accepter la clé de certificat ECDSA extraite par ce module et authentifier `ServerKeyExchange` avec `ecdsa-with-SHA256` avant d’autoriser le calcul ECDHE. Les chaînes ECDSA avec intermédiaires devront ensuite appliquer les mêmes contraintes CA, AKI/SKI, dates, hôte et NameConstraints que le chemin RSA déjà existant.
